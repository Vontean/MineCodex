# Sites 本地与自托管站点扩展：可行性与实施计划

状态：第一版本已实现，隔离窗口验证中，等待用户交互验收。研究日期：2026-09-30。

验证基线：MineCodex 2.0.2；前置聚焦按钮修改已独立提交 `ab35a40`。当前桌面应用版本 `26.924.22138`，build `11645`。

## 1. 用户目标与成功标准

把原生 Sites 变成统一的网页入口：OpenAI 托管站点、本地正在运行的网页服务、用户自托管的网址都可以从这里打开，并保留开发上下文。

一次点击完成：确定聊天目标 → 打开原生浏览器面板 → 收起聊天侧栏 → 让聊天区保持官方最小宽度，将其余空间交给网页。

可检查的成功标准：

1. 保留官方站点原有内容、分享、菜单与打开能力，额外站点出现在相同 Sites 页面。
2. 列表和网格均可使用；搜索、空列表、明暗主题和页面切换不丢失额外站点。
3. 项目来源的新聊天属于正确 project；无项目来源复用原 thread；外部来源使用新的无项目聊天。
4. 打开网址不自动发消息、不自动启动模型任务。已有未发送草稿按原生行为保留，不要求强制清空。
5. 官方和额外站点均可获得宽屏浏览布局；之后手动调整不会被反复覆盖。
6. 本地服务未运行、关联项目/聊天丢失时给出明确恢复入口，不能静默打开错误的上下文。

## 2. 本轮验证结果

所有注入和点击实验均使用独立 profile `/tmp/mcx-session-status-codex-profile`、CDP `9233`。未修改日常窗口，也没有修改 OpenAI 的站点数据、权限或部署。

| 能力 | 证据 | 结论与边界 |
| --- | --- | --- |
| 找到 Sites 原生挂载点 | 实际 DOM 有 `data-testid="sites-table"`、`sites-grid`、`data-appgen-row`；源码中列表/网格来自同一组项目记录 | 可定位并挂载自有条目；所有空态、搜索、分页和 React 重挂载仍需正式验证 |
| 在原生 Sites 中加入条目 | 隔离页面保留 3 条官方记录，额外插入 1 条插件自有本地站点行 | 一次性列表注入成功；不是完整的数据合并或网格实现 |
| 从注入条目回到指定聊天并打开网址 | 点击实验行，经原生路由回到一个已存在的无项目聊天，composer 的 conversation ID 与目标一致，再打开本地网页 | “无项目来源 → 原 thread → 原生浏览器”的链路已跑通 |
| 本地 HTTP 页面 | 临时 loopback 服务在原生浏览器中 `readyState=complete`，页面标题和 H1 正确，实际截图可见内容 | 本地地址可用；不等于服务发现、自动启动或远程端口转发已实现 |
| 外部 HTTPS 页面 | `https://example.com/` 在原生浏览器形成独立页面，读取到完整文档与标题 | 任意普通 HTTPS 地址的基础路径已验证；特定自托管站点的登录、证书、跳转仍需按实际站点验收 |
| 官方 Site | 点击 WeRead 官方条目后原生浏览器加载其真实网址，读取到页面 H1 和内容 | 沿用官方打开路径可行；本次原生编辑路由回落到新聊天草稿，并未保证回到原开发聊天 |
| 自动收起侧栏、扩大网页 | 原生 Hide sidebar + 分栏 End 操作实测聊天区 320 CSS px、网页面板 915 CSS px | 当前 unified 布局可达到官方最小聊天宽度；不能把 320 写死为所有版本/布局的契约 |
| 不写入拖动结束偏好的自动调整 | 自有条目实验找到原生 resizer 的 `setSize(maximumSize)`，未调用 `onResizeEnd` | 原生 setter 可调用；一次实验在侧栏动画尚未稳定时保留约 322px，正式实现必须等布局稳定再取上限 |
| 项目来源的新聊天 | 原生 Start new chat in MineCodex 将草稿切到 MineCodex，显示对应项目和 Local/main | 项目目标切换已验证；未发送内容会保留，用户已接受这一原生行为 |
| 外部来源的新无项目聊天 | 源码有 `activeProject:null` 的新草稿入口；直接广播 `new-projectless-task` 后原草稿文本仍在 | 保留草稿已获用户明确认可；仍需从有项目上下文核验切换到无项目的完整路径 |

临时实验文件保留于 `/tmp/mcx-sites-probe/`，不参与发布。包含本地测试服务脚本、注入脚本及截图；它们不是产品代码。临时测试服务在研究结束后已停止。

## 3. 产品行为

### 3.1 托管位置与开发来源分开记录

两者不能混成一个字段：一个自托管域名也可能由某个 Codex project 开发；一个 localhost 页面也可能由外部工具开发。

| 维度 | 值 | 用途 |
| --- | --- | --- |
| 托管位置 | OpenAI / Local / Self-hosted | 展示网址类型、可用性和来源标识 |
| 开发来源 | Project / Projectless thread / External | 决定在哪个聊天中打开 |
| 访问范围 | 官方访问策略 / 本机地址 / 由站点管理 | 帮助理解访问方式；不伪造权限 |

保留 `Shared with` 的官方权限含义。建议在站点标题的次要信息中显示 Local / Self-hosted 与域名；额外条目的访问列显示“本机访问”或“由站点管理”，不显示无法证实的 Everyone / Only you，也不连接官方分享设置。

这些标识只说明当前打开方式，不负责修改外部服务器的访问权限。本地地址也不能据此承诺服务只对当前用户开放。

自有条目放在 Owned by you；Shared with you 继续呈现官方共享数据。这里的 owned 指用户维护的个人入口，不代表用户拥有外部网站。

### 3.2 点击路由

| 开发来源 | 目标 | 应保持的上下文 |
| --- | --- | --- |
| 有明确 Codex project | 该项目下的新聊天/新草稿 | project ID、host、开发目录；不复用旧开发聊天 |
| 有明确无项目 thread | 原来的 thread | 原聊天身份、历史、宿主；不创建替代聊天 |
| 外部开发，明确没有 Codex 来源 | 新的无项目聊天/新草稿 | 不继承当前项目；已有未发送草稿按原生行为保留 |
| 来源不明、引用失效 | 展示选择/重新关联入口 | 不把“找不到”静默解释成 External |
| OpenAI 托管站点 | 第一阶段保留官方路由，仅增强布局 | 官方本身会读取 latest_edit_context，并可能在无法恢复时回落到草稿 |

用户明确要求官方站点也优化布局；是否将官方站点的路由也改成“有 project 就必建新聊天”尚未明确。初稿默认保留其原生路由，额外站点严格使用上述三分支。若后续决定统一，使用同一来源解析规则扩展，不能将 OpenAI 的 hosting project ID 当成本地开发 project ID。

“新聊天”沿用原生新聊天/草稿机制，不意味着马上启动一次模型运行。用户已明确接受原生机制保留此前未发送内容的边界：不主动清空、不强制隔离出完全空白草稿，也不为了持久化 thread 自动发送“打开这个网页”。External 的“空”主要表示没有既有开发聊天和 project 关联；保留的草稿是已认可的例外。

同一既有 thread 重复打开相同站点时复用已有浏览器 tab，避免堆积。项目和外部来源仍按需求创建新的聊天目标，不把浏览器去重变成复用旧聊天。

### 3.3 网页优先的布局

顺序：确认目标聊天已激活 → 确认浏览器 tab 在目标聊天挂载 → 仅在侧栏展开时收起 → 等待实际工作区宽度稳定 → 读取原生内容面板最大宽度 → 调用原生 resize setter。

当前源码：unified 布局给聊天保留 320px，regular 布局保留 352px；面板本身最小宽度为 320px。实际还受窗口大小、全屏/分栏、左右互换和动画影响。因此使用当前原生 `maximumSize`，不新增百分比设置，也不覆盖 CSS 宽度。

只在用户从 Sites 打开站点时触发一次；普通 Markdown 链接、日常浏览器导航不触发。之后用户拖动、换 tab、切主题时不持续重置。

优先用不调用 `onResizeEnd` 的原生 setter，避免把程序化调整保存为用户常规面板偏好。返回普通聊天时检查临时布局是否仍由本次打开流程拥有，必要时恢复进入前比例；用户手动调整后交还控制权。具体跨聊天持久化范围要在布局阶段验证，不能直接改 localStorage。

窗口太窄时遵循原生限制，不让聊天区低于原生下限，也不自动变成用户未要求的纯网页全屏。侧栏是聊天列表侧栏，左侧原生应用导航栏仍保留。

## 4. 站点如何进入列表

用户已明确：优先从 Codex Projects 中发现具有网页形态的端口服务，在添加站点时展示候选，由用户选择后快捷添加。发现不等于自动收录。

主流程：

1. 用户在 Sites 点击“添加站点”。
2. 默认展示“从项目发现”的候选，按 Codex Project 分组；每项显示可识别的网页名称、URL/端口和可用状态。项目归属在候选中直接说明，无需用户再次手选。
3. 用户选择候选并添加，保存网址和该 Project 的明确关联；已添加项标记为“已添加”，不重复收录。同项目的多个网页入口分别展示。
4. 添加后按项目来源规则打开该 Project 的新聊天及浏览器面板。不需要识别最初启动服务的具体 Thread。
5. 没有合适候选时，可刷新发现结果，或使用次要入口“手动添加网址”，补充自托管域名、外部网页和无法识别的本地服务。

发现从 Codex 项目清单与项目根目录出发，结合监听进程的工作目录、进程关系及明确的项目运行上下文，筛出属于这些项目的服务。项目配置中的端口可以帮助验证，但不能仅凭配置就声称服务正在运行；端口号相同也不能证明属于某个项目。多根目录、工作树、共享父进程等导致归属不明确时，标明待确认，不猜测绑定。

“有网页形态”通过针对候选地址的轻量 HTTP(S) 检查判断：检查 HTML 文档响应，尝试提取页面标题；已知浏览器入口可补充实际路径。纯 JSON API、数据库和调试协议不进入默认网页候选。返回 HTML 只是网页入口的信号，不保证它是正式前端；无法判断的服务允许手动添加。不要枚举全机端口后全部展示，也不扫描所有历史对话猜测归属。

每个候选的 host 必须明确；远程 Project 的 localhost 不能当成本机服务。远程发现与访问只在宿主能力验证后启用，首轮验证明确区分本机已发现和远程尚未检查。

“从当前聊天保存网页”不再作为首版独立入口要求；未来需要时可复用已有来源登记能力。无项目 Thread 或外部来源仍可通过手动添加建立关联。

保留已登记但暂时停机的本地站点，显示“未运行/无法连接”和重试入口。第一版打开流程不自动执行仓库启动命令；服务启动管理另行设计。域名和端口变化允许编辑，不靠标题静默合并不同应用。

## 5. 最小实现结构

拟新增 `features/sites/`，先写对应 `DESIGN.md`，继承原生 Sites 与 Button 的现有 token、布局和明暗模式，不另建一个 Sites 管理网页。

三个职责即可：

1. **站点记录**：维护额外站点的 URL、来源关联和用户可编辑信息。初期少量数据使用现有 MineCodex supportDir 下的原子写入 JSON；不为此新开常驻 HTTP 端口或引入数据库。写操作经 RuntimeHost 串行化；缓存健康状态不写成站点身份。
2. **Sites 页面注入**：读原生页面状态，在插件自有节点中渲染条目；只管理自己的节点，卸载可清理。官方 records/query cache 保持只读。
3. **打开站点协调器**：`openSite(record)` 隐藏来源解析、聊天路由、浏览器打开、尺寸调整的顺序与失败恢复。对调用方返回已打开的目标或明确失败，不散落多组定时点击。

额外站点记录的最小结构：

```ts
type SiteRecord = {
  id: string;
  title: string;
  url: string;
  hosting: 'local' | 'self-hosted';
  origin:
    | { kind: 'project'; projectId: string; hostId: string; sourceThreadId?: string }
    | { kind: 'thread'; threadId: string; backing: 'codex' | 'chatgpt'; hostId?: string }
    | { kind: 'external' };
  updatedAt: string;
};
```

官方站点用单独的只读 adapter 投影，保留 `hostedSiteId` 和 `latest_edit_context`，不强塞进外部站点文件，不上传用户网址到官方 `/websites` API。

项目/聊天身份解析可以借鉴 `features/images/src/thread-metadata.mjs`，但先处理其当前局限：它读取本地状态，目录匹配只是推断，还不能完整代表远程 host 或 ChatGPT-backed thread。显式关联优先于目录推断；不要把整套 Images 功能引入 Sites。

沿用现有 RuntimeHost 的 host action 与 feature page-script 生命周期。浏览器使用原生能力，避免 iframe 对登录、导航、localhost 及嵌入限制的额外约束。原生事件和 React 回调属于内部契约：集中探测、集中适配，契约不匹配时只停用本扩展操作，不阻塞官方 Sites。

不采用：伪造官方 site record、修改官方 query cache、复制 React 管理节点后假装继承事件、直接修改原生 pane 的 style、写死构建 hash 作为长期接口。这些路径看似少几行代码，却会把来源、分享或 React 生命周期搞混。

## 6. 分阶段计划与验收门槛

### 阶段 A：先完成打开契约，暂不扩展完整列表

- 复用原生项目新聊天、无项目新聊天入口；已有未发送内容直接保留。
- 跑通 Project / 原 Projectless thread / External 三条路径，包含正确 host 与 active project。
- 明确本地 Codex、远程 Codex、ChatGPT-backed 来源的能力探测与失败提示；未支持的来源不得静默降级到本地新聊天。
- 等目标稳定后用原生浏览器打开 URL，不发送消息；同 thread 重复打开去重。

验收：检查原 thread 复用是否正确、新聊天目标的 project/host 是否正确、已有草稿是否保留，以及模型未启动状态。保留原生草稿内容是允许的结果，不作为阻塞项。

### 阶段 B：统一网页优先布局

- 对额外条目的打开流程接入一次性布局调整。
- 监听官方 Sites 的明确打开意图，在原生浏览器挂载成功后应用相同调整；分享、菜单、Create 不触发。
- 对左右互换、分栏/全屏、不同窗口宽度做最小回归；核对展开动画结束后的上限。
- 验证用户后续拖动不被覆盖，以及离开站点浏览后的面板偏好。

验收：官方/本地/外部网址都能在保持原生最小聊天宽度的情况下占用剩余空间；失败时网页仍可使用原生打开路径。

### 阶段 C：从项目发现网页服务并快捷添加

- 优先实现 Codex Project → 运行服务 → 网页候选的发现链路，验证项目归属和网页识别准确性。
- 添加入口默认展示按项目分组的候选，支持刷新、快捷添加和已添加状态；无需重复填写 URL 或 Project。
- 实现最小持久化及编辑、移除，手动添加网址作为自托管、外部及未识别网页的补充。
- 校验 HTTP(S) URL；保留必要路径、query/hash，不因过度规范化合并不同网页；不将带凭据的临时 URL 自动长期保存。
- 处理服务停机、项目移动/删除、聊天归档/删除、host 离线、来源重新关联。

验收：真实项目的前端服务能进入候选并直接添加，纯 API/调试服务不混入默认列表；无候选时可刷新或手动添加；项目关联准确，同项目多入口和已添加项处理正确。重启后记录存在，删除登记不删除项目、聊天或服务，并发写入不丢条目。

### 阶段 D：原生页面完整接入

- 接入列表、网格、搜索和空态，明确官方分页与本地条目合并时的排序和显示计数。
- 自有条目使用原生 token；不触发官方分享、统计或发布请求。
- 覆盖 Owned / Shared 切换、进入/退出 Sites、原生 React 重渲染与插件卸载。

验收：官方空列表或搜索无官方结果时，本地匹配项仍可显示；没有重复条目、遗留事件、误导的空态；明暗模式与原生一致。

### 阶段 E：服务状态与完整交付

- 回归项目服务发现中的端口变化、项目移动、同项目多入口和宿主不可达场景。
- 使用小规模已登记站点健康检查；暂停/重启不删除记录。
- 针对路由与身份、记录持久化、卸载清理做有效测试；使用真实隔离窗口验收完整流程。
- 按功能边界提交。版本号、推送、发布和日常安装升级单独执行，不与本轮方案文档混在一起。

## 7. 尚未验证与下一步决策

当前能确认整体技术方向可行，不能把本轮临时注入当作已完成的新功能。

用户于 2026-09-30 明确接受新聊天保留旧草稿，草稿隔离已从要求和风险门槛中移除。后续重点核验无项目目标的上下文切换。其它未完成项包括完整列表/网格生命周期、自动发现的准确率、跨 host/ChatGPT-backed 路由、站点可达性管理及布局偏好恢复。

用户已确认的添加方式：Project 网页服务发现优先，在添加时选择候选并快捷收录；不是全自动收录。手动网址是补充入口。“从 thread 保存”不作为首版独立功能。官方站点保留路由、仅统一布局仍为方案建议。

最有价值的下一步是阶段 A 的隔离原型，补齐所有来源的正确上下文与浏览器关联，原生保留草稿直接接受，再投入列表和发现功能。

### 自动发现触发 Xcode 授权的修正

排查确认 Deco AI 项目的 `serve-sim` 首页会经 `F7 → aZ` 调用 `xcrun simctl list devices booted -j`；当前 Xcode 的 simctl 包装脚本发现 CoreSimulator 版本偏旧后调用 `xcodebuild -runFirstLaunch`，出现安装授权。Sites 的 HTML 探测因此并非对所有本地服务都无副作用。此前将 xcodebuildmcp 列为主要嫌疑的判断已纠正，未禁用插件或修改 Xcode。

修复：监听进程元数据增加完整命令行；在任何 HTTP 请求之前排除 `serve-sim`、`swiftui-preview-browser`，无法读取命令行的进程也不自动探测。普通网页发现与手动网址添加保留。针对性回归 3 项通过；本机只读取进程信息、替换网络探测为空操作，确认 3200 端口被排除。该修复只覆盖自动发现路径；用户主动打开模拟器预览仍可能触发它自身的 Xcode 依赖检查。

## 未启动项目站点：实施进展与后续边界

现有监听端口发现只能回答“什么正在运行”。2026-09-30 只读检查项目配置，发现 VideoGallery/web（Vite）、PortfolioSite（Next）、WereadSite（Astro）、VPN Dashboard/web（Vite）等存在网页启动入口，未运行时均无法通过端口枚举发现。

建议将项目网站目录与运行状态分开：

1. 以 Codex project roots、关联 worktrees 和 workspace 清单为边界，读取 package.json 的脚本、框架依赖及入口文件；静态 HTML 项目单独识别。跳过 node_modules、产物与缓存。不执行配置文件，不凭 dev 脚本名就认定网页：watch 编译、MCP 服务、模拟器桥接不是网站。
2. 项目候选保存 projectId、hostId、相对目录与网页入口，以此去重；URL 是运行后的地址，不能作为唯一身份。一个项目可以有多个网页应用；一个端口也可以承载多个明确页面入口。
3. 添加弹窗继续按项目分组、多选。运行中与未启动的候选都可收录；未启动不从列表消失。端口探测只负责补充在线状态与实际 URL。
4. 已运行则直接打开；有明确启动配方的项目按需启动，成功后进入原生浏览器。脚本含多个服务、缺少依赖、需要环境变量等无法确定的情况交给对应项目聊天处理，不自行安装依赖或执行猜测命令。启动失败明确呈现失败，不无限等待。
5. 记录 MineCodex 自己启动的进程与实际输出 URL，不结束用户原先运行的服务。端口冲突可改变实际地址，不能长期绑定默认端口。启动完成后抓取缩略图；未运行时保留上一次截图，无历史截图则占位，不显示持续 loading。
6. 局域网网站可作为 Custom URL 收录。远程项目的启动、目录发现和端口解析需要已配置的远程连接，在目标机器执行；本机无法仅凭局域网 URL 推断远端项目目录和启动命令。不做全网段端口扫描。

先实现本机常见 Vite / Next / Astro / 静态 HTML 入口识别与持久收录，再接入按需启动和已配置远程项目。扫描不执行启动脚本。

参考：Vite 的 server.port 冲突时会自动尝试后续端口，因此需读取实际运行地址： https://vite.dev/config/server-options
